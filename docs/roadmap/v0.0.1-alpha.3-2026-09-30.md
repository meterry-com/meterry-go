# v0.0.1-alpha.3 Roadmap

Date: 2026-09-30 (tagged commit date)

Change range: `v0.0.1-alpha.2` → `v0.0.1-alpha.3`, through commit `ba2a080`.

## Release Goals

- Configure the project scope once per client to simplify management, query, and event ingestion APIs.
- Support subject-filtered usage-control rule queries and expose concrete limit IDs.
- Add an SDK entry point for issuing short-lived subject JWTs.

## Change Log

### Project-bound clients

- Added required `Config.ProjectID` and made `APIKey` required; initialization trims surrounding whitespace and rejects empty values.
- Project-scoped operations in `Manager`, `Query`, and `Ingest` now use the configured project ID.
- Removed the `ForProject` suffix and `projectID` argument from existing methods for accounts, subject bindings, wallets, voucher grants, usage-control rules, budget leases, usage queries, and bill queries.
- Removed the `projectID` argument from rule-set management, `Query.Report`, event listing and detail queries, and single/batch ingest methods; removed `ChartQuery.ProjectID`.
- The API key authenticates tenant identity. No tenant ID configuration or `X-Tenant-ID` header is required.

### Usage-control rules and limit IDs

- Added `ManagerClient.ListUsageControlRulesBySubject(ctx, subjectType, subjectID)` with server-side subject filtering and automatic pagination; the existing account-filtered entry point is now `ListUsageControlRules`.
- Added `SubjectType` and `SubjectID` to `types.ListUsageControlRulesRequest` and made its `AccountID` JSON field optional.
- Added optional `ID` fields (`id` in JSON) to `types.SubjectRealtimeLimitItem` and `types.VirtualWalletLimitSnapshot`. Compatibility snapshot mapping preserves the ID for deleting individual limits with `DeleteRuleAccountLimit`.

### Subject JWT grants

- Added `ManagerClient.GrantSubject` for `POST /v1/subject/grants`.
- Added `types.GrantSubjectRequest`, `types.GrantSubjectResponse`, and `types.TenantAPIKeyScopeSubjectJWTGrant` (`subject_jwt:grant`).
- Requests accept `SubjectType`, `SubjectID`, `Rules`, optional `Metrics`, and `ExpiresIn`. `Rules` currently supports `analysis`. Omit `Metrics` to allow all metrics, or supply a nonempty list to restrict access. `ExpiresIn` is in seconds and defaults to the server's lifetime when omitted.
- Responses include the token type, access token, lifetime, expiration time (Unix seconds), subject, rules, and optional metrics.
- Grants require a tenant API key bound to the target project with the `subject_jwt:grant` scope. Fixed service API keys cannot issue tokens. The server derives tenant and project identity from the API key, rather than using the client's configured `ProjectID` as the authorization scope.

### Documentation and tests

- Updated README configuration, breaking-change migration guidance, and subject JWT examples.
- Added or updated tests in the tag for initialization validation, configured project routing and authentication headers, limit ID decoding and compatibility mapping, public JSON field constraints, JWT request/response contracts, and propagation of 400, 401, and 403 errors.

## Compatibility Notes and Migration

This release includes breaking API changes. Update calling code when upgrading.

1. Set `ProjectID`, `BaseURL`, and `APIKey` in `sdk.Config`; use a separate client for each tenant/project pair.
2. Remove the `ForProject` suffix and project ID argument from existing calls, for example:

   ```go
   // alpha.2
   account, err := client.Manager.CreateAccountForProject(ctx, projectID, req)
   // alpha.3: projectID is configured in sdk.Config.ProjectID
   account, err := client.Manager.CreateAccount(ctx, req)
   ```

3. Also remove project ID arguments from rule-set, report, event-listing, and ingest methods without a `ForProject` suffix, and remove `ChartQuery.ProjectID`.
4. The legacy wallet-limit wrappers are now `ReadRealtimeWalletLimits` and `ReadVirtualWalletLimits`. They preserve the old snapshot shape and remain deprecated; prefer `ReadSubjectRealtimeLimits`. The realtime balance helper is now `ReadVirtualWalletAmount`.
5. Before using `GrantSubject`, ensure the API key is bound to the configured project and has the grant scope.

## Next Steps

Recommended follow-up migration work:

- Complete project configuration and method signature updates in callers.
- Continue migrating to `ReadSubjectRealtimeLimits`, and revisit removal of the legacy wallet-limit wrappers in a later release.
- Adopt subject-filtered rule queries and JWT grants where needed.
